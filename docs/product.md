# Продуктовая спецификация

## 1. Краткое описание

Silsol - web-приложение для ведения документации с помощью LLM. Пользователь работает с системой через чат: описывает идею, просит добавить раздел, уточнить требование, переписать формулировку или зафиксировать решение. LLM обновляет документацию, а пользователь видит результат в отдельной read-only области.

Главный поток MVP:

```text
Пользователь -> LLM -> Документация
```

В MVP пользователь не редактирует документацию напрямую. Чат является единственным способом изменить содержимое документации.

## 2. Проблема

Команды часто начинают разработку с неполных или разрозненных описаний:

- идея существует только в переписке;
- требования не структурированы;
- решения и причины решений теряются;
- документация быстро устаревает;
- прямое ручное редактирование усложняет контроль происхождения изменений;
- LLM может сгенерировать красивый текст, но без валидации и истории изменений результат сложно контролировать.

Silsol должен решать эту проблему через простую связку: пользователь формулирует намерение в чате, LLM меняет документацию, система сохраняет результат и историю изменений.

## 3. Цели

- Сократить время перехода от сырой идеи к понятной документации.
- Дать пользователю простой интерфейс без ручного Markdown-редактора.
- Сделать документацию главным рабочим артефактом.
- Делать изменения трассируемыми через сообщения чата и историю версий.
- Сохранять текущий документ от повреждения при ошибках LLM.

## 4. Не цели MVP

- Прямое редактирование Markdown пользователем.
- Worker-процесс и фоновые очереди задач.
- Полноценный review и approval gate.
- Генерация production-кода.
- Полноценная multi-user collaboration.
- Управление задачами команды.
- Автономная реализация проекта агентами.
- Интеграции с GitHub, Jira, Linear и Notion.
- Enterprise SSO и сложная ролевая модель.

## 5. Целевые пользователи

### Founder / Product Owner

Хочет быстро превратить идею продукта в живую спецификацию, не разбираясь в структуре технической документации.

### Разработчик / Tech Lead

Хочет получить технически пригодное описание: цели, ограничения, требования, вопросы, решения и риски.

### Аналитик

Хочет вести документацию в одном месте, фиксируя изменения через диалог и историю обновлений.

## 6. Основной пользовательский сценарий

1. Пользователь создаёт проект.
2. Система показывает workspace: слева чат, справа read-only документацию.
3. Пользователь описывает идею или просит изменить документацию.
4. API передаёт LLM текущую документацию и новое сообщение пользователя.
5. LLM возвращает структурированное обновление документации и краткое объяснение изменения.
6. Система валидирует ответ LLM.
7. Если ответ валиден, система сохраняет новую версию документации.
8. Пользователь видит обновлённую документацию и продолжает работу через чат.

## 7. MVP Scope

### Входит в MVP

- создание проекта;
- один пользователь на локальную или личную установку;
- workspace с чатом и read-only просмотром документации;
- создание начальной документации из идеи;
- изменение документации только через чат;
- сохранение сообщений пользователя и ответов LLM;
- сохранение текущего Markdown-документа;
- базовая история изменений документации;
- настройки LLM provider;
- mock provider для разработки и тестов.

### Не входит в MVP

- прямой Markdown-редактор;
- worker и background jobs;
- отдельные панели structured artifacts;
- полноценный review report;
- approval workflow;
- сложное версионирование с immutable approved snapshots;
- экспорт bundle;
- совместное редактирование в реальном времени;
- платёжная система;
- marketplace шаблонов;
- публичные ссылки на документы;
- сложные permissions;
- мобильное приложение.

## 8. Основной документ MVP

MVP может начинаться с одного консолидированного документа `Project Specification`.

Минимальные разделы:

- Overview;
- Goals;
- Non-goals;
- Target users;
- Requirements;
- Open questions;
- Decisions;
- Risks;
- Changelog.

Позже этот документ можно разложить на PRD, Technical Specification, Architecture Overview, API Draft и другие специализированные документы.

## 9. Критерии готовности MVP

- Пользователь может создать проект из сырой идеи.
- Пользователь видит документацию в read-only режиме.
- Пользователь может попросить LLM изменить документацию через чат.
- Система не предоставляет прямое редактирование документации пользователю.
- Система сохраняет новое состояние документации после валидного ответа LLM.
- Ошибка LLM не повреждает текущую документацию.
- Пользователь видит историю или краткое описание последних изменений.

## 10. Основные риски

| Риск | Влияние | Митигирующее действие |
| --- | --- | --- |
| LLM меняет документацию не так, как ожидал пользователь | Высокое | Показывать краткое описание изменения и хранить предыдущие версии |
| LLM выдумывает требования | Высокое | Явно отмечать предположения и открытые вопросы |
| Пользователь не может быстро внести точечную правку | Среднее | Поддерживать короткие команды в чате вроде "замени X на Y" |
| Ошибка LLM повреждает документ | Высокое | Применять изменения только после schema validation |
| Стоимость LLM запросов растёт | Среднее | Лимиты, кеширование контекста, mock provider для разработки |
