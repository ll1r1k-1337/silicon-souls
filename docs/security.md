# Безопасность

## 1. Основные принципы

- Пользовательский ввод считается недоверенным.
- LLM output считается недоверенным.
- Секреты не логируются и не экспортируются.
- Пользователь не редактирует документацию напрямую.
- Prompt injection не должен менять системное поведение.
- Обновление документации применяется только после application validation.

## 2. Данные

Сервис хранит:

- тексты пользовательских идей;
- сообщения чата;
- текущую документацию;
- версии документации;
- summaries изменений;
- metadata LLM вызовов;
- настройки LLM provider.

Потенциально эти данные могут содержать коммерческую тайну, поэтому для production нужны:

- access control;
- backup encryption;
- TLS;
- запрет plaintext секретов;
- audit log для критичных действий.

## 3. Секреты

К секретам относятся:

- LLM API keys;
- database credentials;
- session secrets;
- webhook secrets, если появятся интеграции.

Правила:

- не хранить секреты в git;
- не отправлять секреты на frontend после сохранения;
- маскировать секреты в логах;
- давать пользователю возможность заменить ключ;
- хранить только encrypted или external secret reference.

## 4. Prompt injection

Угроза: пользовательский текст или импортированный документ может содержать инструкции для LLM, которые пытаются изменить правила системы.

Защита:

- system prompt отделён от пользовательских данных;
- пользовательский контент вставляется в промпт как quoted data;
- LLM не может напрямую менять настройки системы;
- LLM не может обойти schema validation;
- публичный UI не имеет прямого Markdown editor;
- suspicious instructions можно отмечать в audit log.

## 5. Document update security

Документация изменяется только через chat endpoint.

Правила:

- read-only documentation endpoint только читает текущее состояние;
- пользовательский UI не вызывает прямой `PATCH markdown`;
- LLM response должен пройти schema validation;
- пустой или невалидный Markdown не заменяет текущий документ;
- каждое успешное изменение создаёт новую версию;
- ошибка LLM не изменяет сохранённый документ.

## 6. Rate limiting

Rate limiting нужен для:

- отправки сообщений;
- LLM-driven обновлений документации;
- диагностических запросов к provider.

Цель:

- защитить бюджет LLM;
- предотвратить abuse;
- уменьшить риск denial of wallet.

## 7. Content safety

Сервис не должен выполнять инструкции из документа как команды ОС, SQL или shell.

Запрещено:

- исполнять код из пользовательского документа;
- использовать generated SQL без review;
- передавать секреты в LLM prompt без явной необходимости;
- писать LLM output напрямую в production config;
- применять LLM output к документации без validation.

## 8. Минимальный security checklist MVP

- `.env` файлы не коммитятся.
- API key маскируется в UI.
- Ошибки API не раскрывают stack trace в production.
- Документация отображается пользователю read-only.
- Прямой пользовательский `PATCH markdown` отсутствует.
- LLM outputs валидируются.
- Ошибка LLM не повреждает текущий документ.
- Логи не содержат plaintext API keys.
