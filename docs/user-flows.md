# Пользовательские сценарии

## 1. Создание проекта из идеи

**Цель:** быстро начать работу над документацией.

1. Пользователь нажимает `New Project`.
2. Вводит название и краткое описание идеи.
3. Система создаёт проект и первую chat session.
4. Система показывает workspace: слева чат, справа read-only документация.
5. LLM создаёт начальный документ или задаёт уточняющие вопросы, если данных недостаточно.

**Результат:** создан проект с документацией, которую можно менять только через чат.

## 2. Просмотр документации

**Цель:** видеть текущее состояние спецификации без риска случайно изменить документ.

1. Пользователь открывает проект.
2. Система загружает текущую документацию.
3. Документ отображается в read-only режиме.
4. Пользователь может читать документ, но не редактировать Markdown напрямую.

**Результат:** документация остаётся единым управляемым артефактом.

## 3. Настройка LLM provider через UI

**Цель:** подключить модель без ручного редактирования `.env` или конфигов на сервере.

1. Пользователь открывает `Settings`.
2. Выбирает provider, например `OpenAI-compatible`.
3. Вводит `Base URL`, `Model` и `API key`.
4. Нажимает `Test connection`.
5. Система отправляет безопасный диагностический запрос через backend API.
6. Если проверка успешна, пользователь сохраняет настройки.
7. UI показывает активный provider и маскированный ключ.

**Результат:** чат использует provider, настроенный пользователем через UI.

## 4. Изменение документации через чат

**Цель:** изменить документ без ручного редактора.

1. Пользователь пишет в чат, что нужно изменить.
2. API сохраняет сообщение пользователя.
3. API передаёт LLM текущее состояние документации и новое сообщение.
4. LLM возвращает обновлённый Markdown и краткое описание изменения.
5. Система валидирует ответ LLM.
6. Если ответ валиден, система сохраняет новую версию документации.
7. Read-only view обновляется.

**Результат:** пользователь изменил документацию через LLM.

## 5. Уточнение требований через диалог

**Цель:** превратить неструктурированное описание в более полную спецификацию.

1. LLM видит пробел в текущем документе.
2. LLM задаёт уточняющий вопрос в чате.
3. Пользователь отвечает.
4. LLM обновляет документацию с учётом ответа.
5. Система сохраняет новую версию и краткое описание изменения.

**Результат:** документация становится полнее без прямого редактирования.

## 6. Точечная правка

**Цель:** позволить пользователю быстро менять конкретные формулировки.

1. Пользователь пишет команду вроде: `Замени "локальная модель" на "OpenAI-compatible provider"`.
2. LLM применяет точечное изменение к документации.
3. Система валидирует и сохраняет обновлённый Markdown.
4. Пользователь видит результат в read-only view.

**Результат:** точечная правка проходит через тот же поток `Пользователь -> LLM -> Документация`.

## 7. Ошибка LLM

**Цель:** не повредить текущий документ при сбое модели.

1. Пользователь отправляет сообщение.
2. LLM возвращает невалидный JSON, пустой документ или ошибку provider.
3. Система не применяет изменение.
4. Пользователь видит понятную ошибку и может повторить запрос.

**Результат:** сохранённая документация остаётся в последнем валидном состоянии.
